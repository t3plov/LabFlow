# Тест-план и тест-кейсы для проекта LabFlow

**Проект:** LabFlow — система управления лабораторными работами
**Версия:** MVP 1.0
**Тип тестирования:** Функциональное, интеграционное, E2E, нагрузочное

---

## 1. Общая информация

Документ описывает стратегию, объём и конкретные тест-кейсы для проверки MVP проекта LabFlow. Тестирование покрывает бэкенд (API, модели, права доступа), фронтенд (шаблоны, роли, UX), Telegram-бота, инфраструктуру (Docker, Nginx) и безопасность.

---

## 2. Цели тестирования

1. Подтвердить корректность работы FSM переходов статусов сдачи.
2. Проверить RBAC-матрицу доступа для всех ролей (Студент, Преподаватель, Староста).
3. Убедиться в корректности вычисления флага `is_overdue`.
4. Проверить полный цикл сдачи лабораторной работы.
5. Проверить работоспособность Telegram-уведомлений.
6. Проверить корректность работы API и соответствие Swagger-документации.
7. Оценить производительность при нагрузке 30 одновременных студентов.

---

## 3. Область тестирования

### В объёме тестирования

- Backend API (B1–B11)
- Frontend (F1–F7)
- Telegram-бот (T1–T5)
- Инфраструктура (Docker Compose, Nginx)
- RBAC и object-level permissions
- FSM статусов
- Вычисление `is_overdue`

## 4. Приоритеты тест-кейсов

Для приоритизации используется методология **MoSCoW**, адаптированная под тестирование:

| Приоритет        | Значение    | Описание                                                                                                                                                                          |
| ---------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Обязательный** | Must have   | Критичные тест-кейсы. Без их прохождения релиз невозможен. Проверяют ключевую функциональность: аутентификация, FSM, RBAC, `is_overdue`, загрузка файлов, основные API-эндпоинты. |
| **Желательный**  | Should have | Важные тест-кейсы. Желательны к прохождению в MVP, но при нехватке времени могут быть отложены: Telegram-уведомления, админ-панель, UX-доработки, E2E.                            |
| **Возможный**    | Could have  | Тест-кейсы для второстепенных функций: удаление лаб, drag&drop, сортировка таблиц. Проходят при наличии ресурсов.                                                                 |

Ниже в тест-кейсах приоритет указывается одним из значений: **Обязательный**, **Желательный**, **Возможный**.

## 6. Тест-кейсы

### 6.1. Инфраструктура (Этап 0)

#### TC-INF-001: Запуск docker-compose

- **Приоритет:** Обязательный
- **Шаги:**
  1. Скопировать `.env.example` в `.env`, заполнить переменные.
  2. Выполнить `docker-compose up -d`.
  3. Проверить `docker-compose ps`.
- **Ожидаемый результат:** Все сервисы (db, backend, nginx) в статусе `Up`, health-check проходит.
- **Связано:** DoD п.1

#### TC-INF-002: Проверка health-check сервисов

- **Приоритет:** Обязательный
- **Шаги:**
  1. Запросить health-endpoint backend.
  2. Проверить доступность БД из backend.
  3. Проверить, что Nginx проксирует `/api/`.
- **Ожидаемый результат:** Все health-check возвращают 200/OK.

#### TC-INF-003: Проксирование через Nginx

- **Приоритет:** Обязательный
- **Шаги:**
  1. Запросить `/api/v1/labs` через Nginx.
  2. Запросить `/static/...`.
  3. Загрузить файл больше `client_max_body_size`.
- **Ожидаемый результат:** API доступен, статика отдаётся, большой файл отклонён с 413.

### 6.2. Аутентификация

#### TC-AUTH-001: Успешный логин

- **Приоритет:** Обязательный
- **Шаги:**
  1. POST `/api/v1/auth/login` с валидными учётными данными.
- **Ожидаемый результат:** 200, токен/сессия, cookie установлена.

#### TC-AUTH-002: Логин с неверным паролем

- **Приоритет:** Обязательный
- **Шаги:**
  1. POST `/api/v1/auth/login` с неверным паролем.
- **Ожидаемый результат:** 401, сообщение об ошибке.

#### TC-AUTH-003: GET /auth/me

- **Приоритет:** Обязательный
- **Шаги:**
  1. Авторизоваться, запросить `/api/v1/auth/me`.
- **Ожидаемый результат:** 200, данные текущего пользователя (role, full_name, email).

#### TC-AUTH-004: Logout

- **Приоритет:** Обязательный
- **Шаги:**
  1. Авторизоваться, POST `/api/v1/auth/logout`.
  2. Повторно запросить `/auth/me`.
- **Ожидаемый результат:** 200 при logout, 401 при повторном запросе.

#### TC-AUTH-005: Доступ без авторизации

- **Приоритет:** Обязательный
- **Шаги:**
  1. Запросить `/api/v1/submissions/my` без токена.
- **Ожидаемый результат:** 401.

### 6.3. FSM статусов

**Матрица разрешённых переходов (уточнить по ТЗ п. 3.2):**

| Из → В                       | Студент | Преподаватель |
| ---------------------------- | ------- | ------------- |
| NOT_STARTED → IN_PROGRESS    | ✅      | ❌            |
| IN_PROGRESS → SUBMITTED      | ✅      | ❌            |
| SUBMITTED → NEEDS_REVISION   | ❌      | ✅            |
| SUBMITTED → ACCEPTED         | ❌      | ✅            |
| NEEDS_REVISION → IN_PROGRESS | ✅      | ❌            |
| NEEDS_REVISION → SUBMITTED   | ✅      | ❌            |
| ACCEPTED → \*                | ❌      | ❌            |
| \* → NOT_STARTED             | ❌      | ❌            |

#### TC-FSM-001: Студент: NOT_STARTED → IN_PROGRESS

- **Приоритет:** Обязательный
- **Шаги:** Студент вызывает PATCH `/submissions/{id}/status` со `IN_PROGRESS`.
- **Ожидаемый результат:** 200, статус изменён, запись в StatusHistory.

#### TC-FSM-002: Студент: IN_PROGRESS → SUBMITTED

- **Приоритет:** Обязательный
- **Ожидаемый результат:** 200, `submitted_at` обновлён.

#### TC-FSM-003: Студент: SUBMITTED → ACCEPTED (запрещено)

- **Приоритет:** Обязательный
- **Ожидаемый результат:** 403, статус не изменён, StatusHistory не пополнена.

#### TC-FSM-004: Преподаватель: SUBMITTED → NEEDS_REVISION

- **Приоритет:** Обязательный
- **Ожидаемый результат:** 200, триггер Telegram-уведомления студенту.

#### TC-FSM-005: Преподаватель: SUBMITTED → ACCEPTED

- **Приоритет:** Обязательный
- **Ожидаемый результат:** 200, уведомление студенту.

#### TC-FSM-006: Недопустимый переход IN_PROGRESS → ACCEPTED

- **Приоритет:** Обязательный
- **Ожидаемый результат:** 400/403.

#### TC-FSM-007: Переход из ACCEPTED в любой статус

- **Приоритет:** Обязательный
- **Ожидаемый результат:** 400/403 для всех ролей.

#### TC-FSM-008: Транзакционность записи в StatusHistory

- **Приоритет:** Обязательный
- **Шаги:** Симулировать ошибку после смены статуса.
- **Ожидаемый результат:** Откат транзакции, статус и история консистентны.

#### TC-FSM-009: Immutability StatusHistory

- **Приоритет:** Обязательный
- **Шаги:** Попытаться обновить/удалить запись StatusHistory через API/ORM.
- **Ожидаемый результат:** Операция запрещена.

### 6.4. is_overdue

#### TC-OVER-001: До дедлайна, статус IN_PROGRESS

- **Приоритет:** Обязательный
- **Ожидаемый результат:** `is_overdue == False`.

#### TC-OVER-002: Ровно в момент дедлайна

- **Приоритет:** Обязательный
- **Ожидаемый результат:** `is_overdue == False` (по формуле `now > deadline`).

#### TC-OVER-003: После дедлайна, статус SUBMITTED

- **Приоритет:** Обязательный
- **Ожидаемый результат:** `is_overdue == True`.

#### TC-OVER-004: После дедлайна, статус ACCEPTED

- **Приоритет:** Обязательный
- **Ожидаемый результат:** `is_overdue == False` (исключение по условию).

#### TC-OVER-005: is_overdue в списках

- **Приоритет:** Обязательный
- **Шаги:** GET `/submissions/my`, GET `/labs/{id}/submissions`, GET `/summary`.
- **Ожидаемый результат:** Поле присутствует и корректно во всех ответах.
